# 05 · 复盘与下一步

## 最难的问题

**「无优先级冲突」与「有优先级冲突」的边界判定。**

题目参考实例明确要求：D01（30 天）与 D02（15 天）冲突且无优先级时，必须**列出冲突并追问**，不能擅自回答 15 天。但我在实现时发现一个隐蔽陷阱——优先级字段里出现「未与 D02 声明优先级」这样的**消极表述**，如果只是朴素地搜关键词「优先」，就会把「未声明优先级」误判成「声明了优先级」，导致 Agent 擅自选 D01 定案，恰好踩中题目的雷区。

**解法**：把优先级判定拆成两层——先识别「积极声明」（为准/最新/以本/高于/优先于），再识别「消极表述」（无/未/不/没有）来排除。这让我深刻体会到：**业务规则里的边界条件，往往藏在自然语言的细微处，靠关键词匹配很难一次写对，必须用测试把正反两条路径都锁住。**

## 最大的工程教训

**LangGraph 的状态合并不是"就地修改"。**

我一开始在决策节点里写 `state["_candidate_docs"] = ...` 想跨节点传数据，结果静默失效（未声明的 key 被合并时丢弃），导致「补充查证」逻辑完全没生效，还花了时间排查为什么 Agent 只读一篇就结束。教训：**框架的状态流转有它自己的语义，先读文档理解"状态如何更新"，再写代码，否则会踩"看起来对、实际不对"的坑。**

## 学习收获

1. **ReAct 的本质是"观察驱动分支"**，不是"跑完流程"。真正体现智能的不是循环本身，而是「读到冲突 → 决定补充查证 or 追问 or 定案」这个**根据结果改变动作**的能力。
2. **离线 Mock 决策器的价值被低估了**。它让整个决策闭环在无 API Key 时也能被测试、被评审复现，还逼我把决策逻辑显式化——反而比黑盒 LLM 更清晰。
3. **测试是安全网，尤其是冲突这种业务规则**。正反两条路径（定案 vs 追问）各写一个测试，改代码时立刻能发现是否破坏边界。

## 未完成部分

- 真实 LLM（`ChatModelDecision`）未做真机实测（离线环境无 API Key）。
- 检索未向量化，仍是朴素 2-gram。

## 下一步

1. **检索升级**：接入 embedding + 向量检索（如 `langchain` 的 FAISS / 或云向量库），提升「流程性 vs 条款性」问题的区分度，缓解「怎么提交」误命中「期限」的问题。
2. **冲突检测升级**：从「数字型条款」扩展到「语义型矛盾」，可引入文本蕴含（NLI）或让真实 LLM 判断两段文本是否冲突。
3. **真实模型验证**：配置 API Key，用 `ChatModelDecision` 跑通「真实模型决策 → 工具 → 观察」闭环，对比 Mock 的决策质量。
4. **对话状态持久化**：接入 LangGraph 的 checkpoint，支持多轮会话真正的状态保存与恢复。
5. **结构化输出**：让最终回答以固定 JSON（answer/citations/gaps/status）返回，便于下游系统消费。
